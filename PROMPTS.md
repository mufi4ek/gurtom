# PROMPTS.md — 24 промпти для coder.qwen.ai

## Як цим користуватися

1. **Створи репозиторій** `mufidev/gurtom` і поклади туди цей пакет:
   `PLAN.md`, `app-notes/DATA_SCHEMA.md`, `.github/workflows/android-build.yml`
   (з `ci/android-build.yml`), а `dataset/gurtom.db.gz` — у `app/src/main/assets/`.
2. **Надішли кодеру ПРОМПТ 0** — він створить скелет проєкту.
3. Далі надсилай промпти **послідовно, по одному**. Не три-чотири одразу:
   кодер втрачає контекст і починає суперечити сам собі.
4. Кожен промпт закінчується вимогою зробити коміт — тож у GitHub одразу
   з'являється код, а Actions одразу збирає APK.

**Три правила, які рятують від 90% проблем:**

- Кожен промпт посилається на `app-notes/DATA_SCHEMA.md`. Не переказуй схему
  руками — хай кодер її читає.
- Вимагай **«не змінюй те, що вже працює»** — інакше кодер переписує попередні
  модулі й ламає їх.
- Після кожного промпта проси **короткий звіт**: які файли створено, що треба
  перевірити вручну, які відомі обмеження.

## ПРОМПТ 3 — Шар даних: БД, DAO, репозиторії, WordFilter

```
Прочитай app-notes/DATA_SCHEMA.md ПОВНІСТЮ — це контракт, відступи від нього
неприпустимі. Також PLAN.md розділ 5.
Працюй у :core:database, :core:common і :data. Не чіпай UI-модулі.

ЗАВДАННЯ: реалізувати шар даних, який видає слова й картки.

1. WordDatabaseAssetUnpacker — точно за DATA_SCHEMA.md §1 (idempotent,
   версіонування через BUILD_DATA_VERSION, робота на Dispatchers.IO,
   тимчасовий файл + rename).
2. WordDatabase: відкриття розпакованого файлу в режимі READ_ONLY.
   Жодних міграцій і записів у цю базу — вона незмінна.
   Окремий файл для користувацьких даних (профілі, статистика, власні
   набори слів): Room-база gurtom-user.db у filesDir.
3. WordEntry (data class) з усіма полями з §2, де JSON-колонки вже
   розпарсені у List<String>. Парсинг — за §2.1, ліниво й безпечно
   (порожній '[]' -> emptyList, битий JSON -> emptyList без crash).
4. WordFilter (data class):
   difficulty: Int?, maxAge: Int, topics: Set<String>, pos: Set<String>,
   excludeProper: Boolean, actableOnly: Boolean, tabooOnly: Boolean,
   kidsOnly: Boolean, phraseMin: Int, phraseMax: Int, maxWordLength: Int?,
   startsWithLetter: String?, excludeIds: List<Long>, limit: Int,
   softCap: Int.
   Плюс фабричні методи WordFilter.alias(difficulty, ages, topics),
   .crocodile(...), .whoAmI(...), .taboo(...), .wordChain(letter, ...),
   .hat(...) — з SQL з §5.
5. WordRepository:
   suspend fun query(filter: WordFilter): List<WordEntry>
   suspend fun existsWord(word: String): Boolean   // для ланцюжка
   suspend fun randomWordStartingWith(letter: Char, maxAge: Int): WordEntry?
   suspend fun countFor(filter: WordFilter): Int
   Обов'язково: AND unsuit=0 AND sens=0 AND age<=:maxAge у КОЖНОМУ запиті.
   Реалізуй фолбек з §5: якщо результат < 20, послаблюй фільтр у порядку
   age -> difficulty -> topics і повертай Pair<List<WordEntry>, FallbackLevel>.
6. PartyRepository: suspend fun cards(kind: PartyKind, maxAge: Int, limit: Int).
   Для kind=emoji повертай data class EmojiCard(puzzle, answer) — розбір
   за §3 (substringBefore/After '|').
7. WordSelector з §6 (виключення повторів, buffer, скидання при вичерпанні).
   Покрий юніт-тестами: не видає дублі, коректно працює при порожній вибірці,
   скидається після softCap.
8. SettingsRepository (DataStore Preferences): theme (dark/light/system),
   accentColor (String hex), language (uk/en/system), maxAge (Set<Int> з 6/12/18),
   reducedMotion, soundEnabled, hapticsEnabled, lastPlayedConfig (JSON),
   adFreeReminderSeen, bigTextScale. Зі значеннями за замовчуванням.
9. Hilt-модулі для всіх репозиторіїв (Singleton для БД, Factory для селекторів).
10. Юніт-тести: WordFilter.alias() будує очікуваний SQL (перевіряй рядок запиту);
    фолбек спрацьовує; WordSelector не повторюється; PartyRepository
    коректно ділить emoji-картку.

ОБОВ'ЯЗКОВО:
- Усі запити — параметризовані (selectionArgs), жодної конкатенації рядків
  користувача в SQL (крім LIKE-патернів для тем, де патерн будується з
  валідованих id зі списку topics.json).
- Ніякого I/O на Main-потіку.
- Не розпарсуй JSON для записів, які не показуються.
- Логи: TAG "GurtomData", рівень Debug, у release-збірці вимкнені.

Зроби коміт "feat(data): sqlite word bank, repositories, WordFilter, tests".
У звіті: скільки записів повертає кожен фабричний фільтр на реальній базі
(додай debug-функцію, яка це друкує), і результати тестів.
```

## ПРОМПТ 4 — Ігровий рушій (спільний для всіх ігор)

```
Прочитай PLAN.md розділи 2 і 5. Шар даних уже готовий (див. app-notes/DATA_SCHEMA.md).
Працюй у :data (engine) і :core:common. Не чіпай репозиторії й дизайн-систему.

ЗАВДАННЯ: створити ігровий рушій, спільний для всіх 10 ігор.

1. Моделі:
   GameType (enum: ALIAS, CROCODILE, WHO_AM_I, TABOO, HAT, WORD_CHAIN,
                   TRUTH_OR_DARE, NEVER_HAVE, MOST_LIKELY, EMOJI, FORFEIT)
   GameSettings(gameType, difficulty: 1..3, ages: Set<Int>, topics: Set<String>,
                roundSeconds, players: List<Player>, teams: List<Team>,
                skipPenalty: Boolean, allowProper: Boolean)
   Player(id, name, avatarId, teamId?), Team(id, name, color)
   GamePhase(SETUP, COUNTDOWN, PLAYING, ROUND_RESULT, PAUSED, GAME_OVER)
2. GameEngine (клас у :data, без Compose):
   - керує станами через StateFlow<GameState>
   - RoundTimer: відлік від roundSeconds, тікає кожні 100 мс, події
     onWarning (10 с), onTick(remaining), onFinish. Реалізуй через
     coroutine + SystemClock.elapsedRealtime (не delay-накопичення,
     щоб не "пливло").
   - Pause/Resume: зупиняє таймер, зберігає залишок.
   - TeamRotator: порядок ходів за командами, перехід після раунду.
   - ScoreKeeper: hit/miss/skip, підрахунок очок команди, визначення
     переможця, паритет.
   - CardDeck: тягне слова через WordSelector з відповідним WordFilter
     для GameType; для HAT — фіксує набір слів на всю гру і пере
     використовує його в трьох раундах (round1 explain, round2 show,
     round3 oneWord з додатковим фільтром words=1 AND length(w)<=12).
3. RulesPolicy — окремий клас, що описує правила кожної гри
   (чи є таймер, чи є команди, чи потрібне слово-картка, чи потрібні
   заборонені слова, чи є ліміт питань). Використовуй його у ViewModel,
   щоб не плодити if-ланцюжки.
4. TabooCardBuilder: формує 5 заборонених слів за алгоритмом із
   DATA_SCHEMA.md §5 (саме слово -> корінь -> hyp -> syn -> hypo -> mer ->
   добір з теми з прапорцем weak=true). Покрий юніт-тестами, включно з
   випадком, коли зв'язків менше 5.
5. WordChainValidator: остання значуща літера (відкидаємо ь й ' ’),
   перевірка через WordRepository.existsWord, відхилення повторів
   (в межах ланцюжка), таймер 15 с на хід. Юніт-тести: "хліб"->"балкон" ОК,
   "кіт"->"тісто" ОК (ігнорує м'який знак... перевір реальну поведінку й
   опиши її), повтор — відхилено.
6. GameState має містити: phase, currentCard (WordEntry?), remainingMs,
   score, currentTeamIndex, roundIndex, questionsAsked (для WHO_AM_I
   ліміт 20), usedCardIds.
7. Збереження стану: GameState має бути Parcelable/Serializable, щоб
   SavedStateHandle переживав поворот екрана й смерть процесу.
   Покрий тестом: serialize -> deserialize -> equals.
8. Юніт-тести обов'язкові для: ScoreKeeper (усі гілки), TeamRotator,
   RoundTimer (з віртуальним часом Turbine/корутин-тест), TabooCardBuilder,
   WordChainValidator, CardDeck для HAT.

ОБОВ'ЯЗКОВО:
- Engine не знає про Compose, Context, Activity. Тільки Kotlin і coroutines.
- Таймер не залежить від швидкості тіків (рахуй від elapsedRealtime).
```

## ПРОМПТ 14 — Локальне лобі: TCP-сервер на хості

```
Прочитай PLAN.md розділ 6 (локальне лобі) ПОВНІСТЮ — там специфікація
протоколу. Працюй у :feature:lobby і :data. Створи :core:network якщо
потрібно. Не чіпай ігрові модулі (інтеграцію зробимо наступним промптом).

ЗАВДАННЯ: реалізувати ХОСТ лобі (сервер).

1. LobbyServer (Kotlin coroutines + java.net.ServerSocket, порт 47820):
   - bind на 0.0.0.0, accept у циклі на Dispatchers.IO
   - кожне з'єднання — окремий coroutine, newline-delimited JSON
     (використовуй kotlinx.serialization, @Serializable data-класи
     для всіх типів повідомлень із PLAN.md §6.4)
   - макс. 8 клієнтів; понад — відповідай REJECT{reason:"room_full"}
2. Стани хоста: IDLE -> HOSTING(roomCode, players, settings) -> IN_GAME.
   roomCode — 4 символи (без неоднозначних 0/O/1/I), генерується випадково.
3. Обробка повідомлень за протоколом:
   HELLO -> перевірка версії застосунку; якщо відрізняється major-версія,
            відповідай VERSION_MISMATCH{minVersion}, інакше WELCOME
   READY  -> онови стан і розішли LOBBY усім
   RESULT -> зарахуй очко, розішли SCORE
   PING   -> PONG з тим самим ts
   BYE    -> видали гравця, розішли LOBBY
   Таймаут: якщо від клієнта немає PING 10 с — познач DISCONNECTED,
   через 30 с — видалити з гри (з повідомленням іншим).
4. Авторитетність: хост володіє WordSelector і генерує карти.
   У START надсилає seed, у TURN — конкретну карту тільки тому гравцю,
   чий хід (або broadcast, якщо карта публічна, як у "Ніколи не").
   Клієнт НЕ отримує весь пул слів (PLAN.md §6.4).
5. Синхронізація таймера: хост надсилає deadlineEpochMs; клієнт рахує
   зсув свого годинника через PING/PONG (offset = (pongRecvTs - pingSendTs
   - rtt/2)). Зберігай середнє з 5 останніх вимірів.
6. IP хоста: отримуй через NetworkInterface.getNetworkInterfaces() —
   фільтруй interfaces, які up && !loopback && мають IPv4 site-local.
   Якщо їх кілька (Wi-Fi + хотспот) — показуй УСІ в списку, з підписом
   імені інтерфейсу. Це важливо: на хотспоті адреса зазвичай 192.168.43.1.
7. Екран хоста:
   - Великий room code
   - Список знайдених IP:портів (кожен із кнопкою "копіювати")
   - QR-код із payload gurtom://join?ip=...&port=...&room=...&v=...
     Генерація QR — локально ( ZXing core, без камери; дозвіл CAMERA
     НЕ потрібен для генерації). Додай залежність com.google.zxing:core.
   - Кнопка "Увімкнути точку доступу" -> Intent
     Settings.ACTION_WIRELESS_SETTINGS (або ACTION_WIFI_TETHER_SETTINGS
     з фолбеком, бо на різних OEM різні)
   - Список під'єднаних гравців з аватарками і статусом ready
   - Налаштування гри (як у Setup) — синхронізуються через LOBBY
   - Кнопка "Почати" активна коли >= 2 гравці ready
8. Життєвий цикл: сервер має коректно зупинятися в onStop (якщо гра
   не йде) і відновлюватися. Використовуй foreground service ТІЛЬКИ
   якщо гра триває у фоні (інакше не потрібен — не ускладнюй дозволи).
   Якщо foreground service потрібен — тип dataSync, з нотифікацією.
9. Юніт-тести: серіалізація/десеріалізація всіх типів повідомлень;
   логіка roomCode (немає неоднозначних символів); розрахунок часового
   зсуву; обробка VERSION_MISMATCH; від'єднання гравця після таймауту.
   Інтеграційний тест: підніми сервер на localhost, підключись клієнтом,
```
